# 假人系统开发交接文档

# 1. 交接目标与适用范围

## 1.1 交接目标

本文档用于向后续开发者交接 RGB-D 假人系统的整体架构、模块职责、数据接口、运行方式、关键决策、已知问题和后续开发方向。

它不是单纯的验收记录。接手者应通过本文档了解系统当前如何运行、代码位于哪里、修改一个模块可能影响哪些链路，以及遇到问题时应从哪里排查。

## 1.2 交接范围

交接内容包括：

- RGB-D 相机接入、数据格式和坐标变换；
- RTMDet、RTMPose/RTMO 与 Halpe26 二维姿态；
- 深度恢复、三维滤波、质量门控、骨长约束和多人跟踪；
- 火柴人、Mixamo/SMPL 假人和动作重定向；
- FastAPI WebSocket Hub 与前端实时显示；
- x86 GPU、Jetson Orin Nano 和 3DGS 场景部署；
- 当前实现状态、运行命令、已知限制和后续任务。

## 1.3 系统边界

系统的主要数据流如下：

```text
RGB-D 相机
    ↓
二维人体姿态
    ↓
Halpe26 三维骨架
    ↓
滤波、质量门控和骨长约束
    ↓
假人动作重定向
    ↓
火柴人 / Mixamo / SMPL 显示
    ↓
WebSocket 前端与 3DGS
```

算法端生成三维骨架，后端负责发布，前端负责显示和假人渲染。主姿态 WebSocket 只传输处理完成后的三维关节，不传输 RGB、深度、二维骨架或假人网格。调试时可另开一条独立 WebSocket，以 latest-only JPEG 二进制帧显示已画好 Halpe26 二维骨架的 RGB 预览；该连接不传深度图，也不参与三维假人驱动。

## 1.4 统一开发约定

### 1.4.1 模块顺序

理解和排查问题时，按“相机 → 二维姿态 → 三维恢复 → 时序约束 → 假人 → 前端 → 部署”的数据流定位，避免同时修改多个关键模块。

### 1.4.2 坐标与单位

几何数据统一使用米制和右手坐标系。相机、应用、Three.js 与 3DGS 坐标的定义和转换必须在接口处明确，且每次只转换一次。

### 1.4.3 无效数据处理

无法确认的深度、关节或几何结果标记为无效，交由时序预测或前端隐藏处理，不能用背景、地面或原点填充。

### 1.4.4 实时数据策略

相机、推理、WebSocket 和渲染链路采用 latest-only 策略，只保留最新数据，避免因等待旧帧、网络或渲染造成延迟积累。

### 1.4.5 修改与追踪

修改代码或配置时，应同时记录影响范围、运行命令、输入数据、模型版本和结果位置；发现问题时先确认数据、坐标和接口，再调整算法参数。



# 2. 系统总体架构与开发边界

## 2.1 系统定位与总体数据流

本系统从 RGB-D 相机恢复 Halpe26 三维骨架，经场景坐标映射驱动假人在 3DGS 场景中移动；浏览器主要用于实时显示、交互和调试。

```text
RGB-D 相机
    ↓
二维姿态 → 深度恢复 → 三维滤波与约束
    ↓
应用坐标系 Halpe26 三维骨架
    ├── 场景坐标映射（出生点、旋转、尺度）
    │        ↓
    │   3DGS 场景中的假人空间移动
    └── WebSocket Publisher
             ↓
       FastAPI Topic Hub
             ↓
       浏览器火柴人 / Mixamo / 3DGS 显示
```

姿态服务负责生成骨架，实时网关负责转发，场景与显示端负责坐标映射和渲染；各层不重复执行其他层的推理或数据处理。

## 2.2 模块边界与代码位置

| 模块 | 主要职责 | 主要位置 |
| --- | --- | --- |
| 相机与姿态 | 读取 RGB-D、二维检测、Halpe26 转换 | `src/rgbd_avatar/live/`、`src/rgbd_avatar/pose/` |
| 深度与三维跟踪 | 深度恢复、滤波、质量门控、骨长约束、多人跟踪 | `src/rgbd_avatar/depth/`、`src/rgbd_avatar/tracking/`、`src/rgbd_avatar/live/` |
| 假人与重定向 | SMPL/Mixamo 加载、骨骼映射、蒙皮和缓存 | `src/rgbd_avatar/avatar/`、`src/rgbd_avatar/retargeting/` |
| 本地查看器 | RGB、二维/三维骨架和假人显示 | `src/rgbd_avatar/visualization/` |
| 实时通信 | WebSocket 发布、Hub 和事件转发 | `src/rgbd_avatar/live/stickman_websocket.py`、`3DGSAlgPlatform/fronted/backend-fastapi/` |
| 前端与场景 | 浏览器显示、场景坐标映射和 3DGS 渲染 | `3DGSAlgPlatform/fronted/fronted-react/` |

`scripts/` 只负责命令行参数和流程启动；可复用算法与数据契约放在 `src/rgbd_avatar/`。

## 2.3 运行模式

| 模式 | 用途 | 主要入口 |
| --- | --- | --- |
| 离线/目录回放 | 检查深度、骨架、假人和问题帧；目录模式模拟实时输入 | `process_rgbd_sequence.py`、`view_pose3d_sequence.py`、`view_live_mannequin.py --source directory` |
| SDK 实时 | 直接读取 MRDVS 内存帧，进行实时姿态、多人和 WebSocket 联调 | `inspect_lx_camera.py`、`view_live_mannequin.py --source sdk`、`view_live_multi_person.py` |
| Jetson 生产 | TensorRT FP16、无 GUI、最多 4 人的边缘实时服务 | `view_live_multi_person_tensorrt.py`、`app.realtime_app:app` |

目录回放的帧率受文件落盘速度限制，不代表相机实时帧率。SDK 相机只能由一个进程独占。

## 2.4 核心数据接口

- **相机帧**：提供 RGB、对齐到 RGB 的米制深度、运行时内参和传感器时间戳；
- **三维骨架**：固定 26 个 Halpe26 关节，无效关节使用 `null`，应用坐标采用米制右手系、`+Z` 向上；
- **实时事件**：单人使用 `avatar.stickman.updated`，多人使用 `avatar.stickmen.updated`，前端从 Hub 转发后的 `message.payload` 读取数据。

场景映射使用出生点、旋转和尺度将应用/局部坐标转换到 3DGS 坐标，核心目标是保持假人在场景中的初始位置、朝向和真实移动距离。完整字段定义见第 15、20 章。

## 2.5 当前主路径与实验项

当前主路径为：SDK 采集 → Halpe26 三维骨架 → 时序/几何约束 → 3DGS 场景坐标映射 → 假人空间移动，并通过 WebSocket 提供浏览器显示。

Jetson 生产路径固定使用 TensorRT FP16、`depth_connected`、`geometry`、最多 4 人、realtime-only FastAPI 和单 worker。

以下属于可独立对比的实验项：`shadow` 身份跟踪、`hybrid`/`guided_window`/`adaptive_hybrid` 深度恢复、RTMO、Gaussian 渲染整合以及 Viser/Filament 查看器。3DGS 坐标映射和假人空间移动本身不属于实验项，而是当前目标。

## 2.6 交接注意事项

1. Nano 使用 `app.realtime_app:app`；完整业务后端 `app.main:app` 依赖数据库和对象存储。
2. FastAPI Hub 是进程内实现，必须使用一个 worker。
3. TensorRT Engine 与具体 Jetson、TensorRT、CUDA 和构建配置绑定。
4. `smpl_sequence.npz`、`mixamo_sequence.npz` 是离线缓存，不是实时接口；前端不重新执行姿态或深度推理。
5. 出现异常时，优先检查相机占用、topic/event、坐标转换和发布端与 Hub 的协议是否一致。

## 4.1 设备与连接

- 相机地址：`192.168.1.125:3956`；
- Nano 相机网卡地址：`192.168.1.188/24`。

## 4.2 RGB-D 数据输入

输入端只向后续算法提供配对的 RGB 和深度帧。当前数据约定为：

- RGB 和深度分辨率：`816×612`；
- 相机帧率：约 `15 FPS`；
- 深度原始单位：毫米，进入算法后转换为米；
- 深度已通过 `DEPTH_TO_RGB` 对齐到 RGB，尺寸和像素坐标一致；
- 使用传感器时间戳驱动后续时序处理。

SDK 适配器还负责将 RGB888 转为 OpenCV 使用的 BGR，并复制 SDK 管理的图像缓冲区，避免下一帧覆盖正在处理的数据。对齐后应重新读取运行时内参，不能只使用写死的分辨率或内参。

## 4.3 输入方式与目录结构

系统保留两种输入方式：

1. **SDK 实时输入**：默认方式，直接从相机内存帧读取，避免 Viewer 落盘和文件解码。启动前可先执行：

   ```bash
   cd /home/fr1511b/program/workspace/humanpose
   conda activate rgbd-avatar
   PYTHONPATH=src python scripts/inspect_lx_camera.py --frames 30
   ```

   采集探测正常后，运行主链路时使用 `--source sdk`。

2. **目录输入**：用于离线回放和无相机调试，使用 `--source directory`。目录中的 RGB 与深度文件必须具有相同时间戳前缀并完整配对，例如：

   ```text
   YYYYMMDD_HHMMSSmmm_r.png
   YYYYMMDD_HHMMSSmmm_d.pgm
   ```

   目录模式默认处理最新的完整帧，不应作为真实 `15 FPS` 的性能依据。

## 4.4 输入端注意事项

- 相机网与 Nano 管理网分开；SSH 使用管理网地址，不使用 `192.168.1.188`。
- 不要随意修改相机内参、RGB/深度工厂对齐参数或 `DEPTH_TO_RGB`；相机安装到应用场景的外参应单独配置。
- 只处理 RGB-D 完整配对的帧；强度图和 PCD 不应阻塞实时姿态更新。

- 目录输入和实时链路都采用 latest-only 策略，处理不过来时丢弃过期帧，不积累等待队列。

# 5. humanpose 后端

## 5.1 后端职责与代码结构

humanpose 负责将 RGB-D 帧转换为稳定的 Halpe26 三维骨架，并向本地查看器、WebSocket 和场景端提供结果。它不负责浏览器渲染，也不在前端重复执行姿态或深度推理。

| 模块 | 主要位置 | 职责 |
| --- | --- | --- |
| 姿态后端 | `src/rgbd_avatar/pose/` | RTMPose、RTMO 实验和 TensorRT 推理，统一输出 `Pose2D` |
| 深度恢复 | `src/rgbd_avatar/depth/` | 深度采样、反投影、连通域和点云恢复，输出 `Pose3D` |
| 时序与约束 | `src/rgbd_avatar/tracking/` | One Euro、短时预测、质量门控和骨长约束 |
| 实时数据边界 | `src/rgbd_avatar/live/` | 相机源、单人/多人处理、坐标变换和 WebSocket 发布 |
| 启动入口 | `scripts/view_live_mannequin.py`、`scripts/view_live_multi_person.py`、`scripts/view_live_multi_person_tensorrt.py` | 组装配置并启动处理链路 |
| 配置 | `configs/camera.yaml`、`live.yaml`、`pose.yaml`、`tracking.yaml` | 相机、模型、恢复、跟踪和发布参数 |

单人链路为：

```text
RGBDSource → RGBDFrame → Pose2D → 深度恢复 → Pose3D
    → 时序滤波/质量处理 → 骨长约束 → 应用坐标 → 查看器/WebSocket
```

多人链路在此基础上增加身份关联、每人独立的时序状态和多人消息封装。

## 5.2 二维姿态与 Halpe26

`src/rgbd_avatar/pose/halpe26.py` 是唯一的关键点名称、编号和骨架连接定义。`Pose2D` 固定包含 `26×2` 的像素坐标、26 个关键点置信度、人体框和框置信度，后续模块不得改变顺序或自行增加关键点。

当前默认后端是 RTMPose-M + RTMDet 人体检测器：

- 配置在 `configs/pose.yaml`，模型输入为 Halpe26 `256×192`；
- `detector: auto` 使用人体检测框，默认阈值为 `0.3`；
- 至少保留 10 个有效关键点，且平均关键点置信度不低于 `0.3`；
- 单人入口取排序后的第一人，多人入口保留检测列表并限制人数。

RTMO 是显式启用的实验后端。它输出 COCO17，再补齐 Halpe26 的 `head`、`neck` 和 `hip`，细分足部关键点保持无效，因此不能直接替代当前需要足部数据的生产路径。

Nano 使用独立的 `TensorRTHalpe26Backend`，由 RTMDet-M `640×640` 和 RTMPose-M Halpe26 `256×192` 两个 FP16 Engine 组成，输出格式仍与 PyTorch 后端一致。

## 5.3 三维骨架恢复

三维恢复使用与 RGB 对齐的米制深度和运行时内参，将二维像素反投影为相机坐标。`Pose3D` 同时保存三维坐标、有效标志、姿态置信度、深度值和深度置信度；无法确认的关节保持无效，不用背景、地面或原点填充。

当前恢复方式分为：

- `window_median`：逐关节局部窗口取深度，作为简单基线；
- `pointcloud_cluster`：建立有组织点云，按人体区域和局部连通表面选择深度，当前单人主路径使用；
- `depth_connected`：在多人链路中按人物区域复用深度连通组件，当前 Nano 多人路径使用；
- `guided_window`、`hybrid`、`adaptive_hybrid`：用于对比和异常关节补救，属于实验配置。

当前有效深度范围为 `0.3～6.0 m`。点云恢复还包含人体拓扑、面部、足部和自遮挡检查；如果局部表面无法确认，宁可让该关节无效，交给后续时序或运动学处理。

## 5.4 时序与几何处理

处理顺序是“人体存在判断 → 三维质量门控 → 时序滤波/短时预测 → 骨长约束”。

- **画面边界门控**：顶部或左右边界的人体默认视为被截断；底部接触只有在足部仍可见时才保留。确认离场后会隐藏输出，并等待人体完整回到画面再恢复。
- **三维质量门控**：多人路径至少需要 8 个有效关节和 3 个躯干关节，并检查躯干深度跨度、深度跳变和人体连接长度；异常分支可以单独失效，整个人体几何失效时不创建或续接轨迹。
- **One Euro 与预测**：单人使用 `tracking.yaml` 的低频滤波配置；多人使用 `live.yaml` 中更适合实时帧率的共享截止频率，并将短时预测限制在 `0.12 s`。时间戳必须使用相机传感器时间，不能用循环次数代替。
- **骨长约束**：`BoneLengthCalibrator` 用当前轨迹的可靠观测建立临时骨长先验，`BoneLengthConstraint` 对预测点和低置信度点做有界投影，固定关节索引 `19`（hip）作为根部锚点。骨长先验只对当前轨迹有效，不应当当作通用人体身高标定。
- **运动学补偿**：多人路径可根据历史骨长和当前二维射线补齐短时缺失的腕、踝等末端点。输出会记录 `joint_sources`，后续显示端不得把补偿点当成原始观测点。

## 5.5 多人与身份跟踪

多人处理由 `LocalMultiPersonPoseProcessor` 负责，每条轨迹独立保存二维观测、三维时序状态、存在门控、骨长先验和深度引导历史。

- 当前默认身份方法为 `geometry`，依据人体框、关键点、根节点和历史位置关联检测结果；
- `shadow` 可增加 RGB-D 外观和遮挡处理，但发生异常时会自动回退到 `geometry`，当前 Nano 不作为默认路径；
- 生产最多处理 4 人；轨迹短时缺失时内部暂存，但对外 `observed_in_frame=false` 且所有关节不可渲染，超过 `0.35 s` 后释放轨迹并重新分配 ID；
- 新检测必须先通过三维有效性和质量检查，不能仅凭二维检测结果创建或续接轨迹。

多人结果中的 `track_id` 是运行期 ID，进程重启后不保证连续；前端和 3DGS 端应以当前消息中的 ID 管理假人实例。

## 5.6 坐标管理与实时输出

相机坐标采用右手系：`+X` 向右、`+Y` 向下、`+Z` 向前，单位为米。应用外参由 `ApplicationExtrinsics` 执行：

```text
p_application = Rz(yaw) · Ry(pitch) · Rx(roll) · p_camera + t
```

当前配置中的应用外参位于 `configs/live.yaml`；应用层输出统一为米制、右手系、`+Z` 向上、地面 `Z=0`。坐标转换只在后端边界执行一次，前端和 3DGS 端不得再次交换轴或重复应用相机外参。

单人发布使用 `avatar.stickman.updated`，多人发布使用 `avatar.stickmen.updated`。消息包含 Halpe26 固定顺序、帧号、毫秒时间戳、状态和 `[x,y,z]` 关节数组；无效关节为 `null`。多人消息还包含 `track_id`、`observed_in_frame`、`joint_sources` 和身份方法。

humanpose 的常规输出是 **application 坐标**。只有显式使用 `LiveSceneMapper` 时才转换为 `3dgs_world`，这样可以避免把场景出生点和人体姿态混在算法后端中。

## 5.7 运行模式与性能配置

配置优先级为“命令行参数覆盖 YAML”。常用方式如下：

```bash
cd /home/fr1511b/program/workspace/humanpose
conda activate rgbd-avatar

# x86 单人实时
PYTHONPATH=src python scripts/view_live_mannequin.py \
  --source sdk --device cuda:0 \

# x86 多人实时
```

## 5.8 Jetson Orin Nano 运行方式

Nano 的生产入口是 `scripts/view_live_multi_person_tensorrt.py`，当前固定为：

- RTMDet-M + RTMPose-M Halpe26 TensorRT FP16；
- `geometry` 身份跟踪、`depth_connected` 三维恢复、最多 4 人；
- 默认检测器间隔为 2，`depth_connected` 完整刷新间隔为 3；需要逐帧排查时将两个环境变量都设为 `1`；
- `--headless --publish-stickmen` 将结果发布到 Nano 本机的 `ws://127.0.0.1:8000/api/realtime/ws`。

Nano 使用设备专用的 `configs/live.nano.yaml` 和本机生成的 TensorRT Engine。ONNX 可以从 x86 复制到 Nano，但 Engine 必须在目标 Nano 上构建；JetPack、CUDA 或 TensorRT 变化后需要重新构建。原生 PyTorch/MMPose 入口保留用于对照，不作为当前生产入口。

## 5.9 后端问题定位

按数据流逐层定位：

1. 无帧或帧号不匹配：检查相机占用、SDK 配置、RGB-D 对齐和 `RGBDSource` 统计；
2. 无二维人体：检查 RGB/BGR 顺序、模型权重、检测器和 `Pose2D` 质量阈值；
3. 二维正常但三维为空或弯折：检查深度单位、内参、有效深度范围、恢复方式和质量门控日志；
4. 姿态抖动或骨架拉伸：先检查时间戳和轨迹 ID，再检查 One Euro 与骨长配置，不要直接放大预测时长；
5. 后端正常但网页无数据：检查发布端 URL、event/topic、`sent/ack` 统计和 FastAPI 是否以单 worker 运行。

修改后优先运行对应模块的单元测试和离线回放，再进入 SDK 实时链路；不要同时更换模型、深度恢复方式、坐标外参和滤波参数。

# 6. 3DGSAlgPlatform 平台端

3DGSAlgPlatform 负责接收 humanpose 发布的三维姿态，加载 3DGS 场景，并在浏览器中显示和驱动假人。平台端不重新执行相机采集、二维检测或三维恢复。

## 6.1 平台结构与服务边界

平台端由以下部分组成：

| 部分 | 主要位置 | 作用 |
| --- | --- | --- |
| FastAPI 实时网关 | `fronted/backend-fastapi/app/realtime_app.py` | 接收、转发实时消息，维护 WebSocket 连接 |
| React 场景前端 | `fronted/fronted-react/src/pages/SceneViewer/` | 加载 3DGS 场景、解析姿态、管理假人实体 |
| 假人资源与重定向 | `fronted/fronted-react/public/假人/mixamo-avatar-delivery/` | 提供 GLB 模型、坐标转换和 Mixamo 骨骼重定向 |
| 场景运行时 | `SceneViewer/runtime/` 及相关 `SparkViewer` 模块 | 管理 3DGS 场景和 Three.js 渲染对象 |

实时数据链路为：

```text
humanpose
    ↓ WebSocket 发布
FastAPI RealtimeHub
    ↓ topic 转发
React SceneViewer
    ↓ 坐标转换、假人重定向
Three.js 假人 + 3DGS 场景
```

当前部署中，Nano 运行 humanpose 和实时网关，浏览器负责 3DGS 加载与渲染；不要把浏览器端的 3DGS 渲染误认为 Nano 端的推理任务。

## 6.2 FastAPI 实时网关

当前实时入口是 `app.realtime_app:app`，提供：

- `GET /api/health`：检查网关是否运行，正常返回 `status=ok`；
- `WS /api/realtime/ws`：实时消息通道。

网关使用进程内 `RealtimeHub` 管理连接和 topic。客户端连接后先注册身份，再订阅指定 topic；humanpose 作为发布端，浏览器作为订阅端。常用控制消息如下：

| 消息 | 用途 |
| --- | --- |
| `hello` / `identify` | 声明客户端类型和 ID，并可同时订阅 topic |
| `subscribe` / `unsubscribe` | 增加或取消 topic 订阅 |
| `publish` | 向 topic 发布业务事件 |
| `ping` | 保持连接并获取 `system.pong` |

连接建立后会收到 `system.welcome`；发布端收到 `system.ack`，订阅端收到 `type=event` 的业务消息。该 Hub 不落盘、不跨进程共享，因此 FastAPI 必须使用单 worker：

```bash
uvicorn app.realtime_app:app --host 127.0.0.1 --port 8000 --workers 1
```

多 worker 会产生多个互相隔离的 Hub，导致发布端和浏览器连接到不同进程时无法互相收到消息。

## 6.3 前端与假人显示

`SceneViewer` 同时管理 3DGS 场景和假人显示。实时模式的主要组件为：

- `useStickmanRealtime`：建立 WebSocket、校验事件、维护最新一帧和重连状态；
- `useStickmanActorEntities`：按实时轨道创建或移除 `realtime` 假人实体；
- `useStickmanRenderer`：绘制 Halpe26 火柴人；
- `useStickmanAvatarRenderer`：加载 `character-a.glb`，使用 `MixamoRetargeter` 驱动蒙皮假人；
- `MotionModePanel`：切换预设/实时模式，配置出生点、朝向和 RGB 预览开关；
- `useRgbSkeletonPreview` + `RgbSkeletonPreviewWindow`：通过独立连接接收 latest-only JPEG，管理重连、过期状态和浮动预览窗。

前端的三维驱动仍只使用 26 个关节坐标，不使用 RGB 预览来推理或修正姿态；预览窗只消费已绘制的 JPEG，不接收深度图、网格或逐帧蒙皮顶点。火柴人和 Mixamo 假人共用同一条 JSON 姿态数据，切换显示模式不需要重新建立姿态 WebSocket。

实时轨道以 `source_id` 或 `source_id + stream_id + track_id` 作为角色身份。第一帧缺失或不完整姿态到达后，前端保持最后一份完整姿态最多 150 ms，不拼接不同帧的关节；超时后只隐藏角色，保留同一 `track_id` 的火柴人/Mixamo 运行时约 1.5 s 后才释放。在保留期内恢复时复用原对象，新 `track_id` 绝不继承旧姿态。

## 6.4 WebSocket 数据接入

前端默认根据当前页面地址生成同源地址：

```text
ws(s)://<host>/api/realtime/ws
```

实时火柴人默认 topic 为：

```text
avatar:stickman:FF6690772788
```

浏览器连接时使用 `client_type=browser`，并在 `hello` 中再次声明该 topic。前端只处理满足以下条件的消息：

- 外层 `type` 为 `event`，且 topic 包含当前订阅 topic；
- `event` 为 `avatar.stickman.updated` 或 `avatar.stickmen.updated`；
- `payload.schema_version=1`、`keypoint_format=halpe26`；
- 坐标系为右手、米制、`+Z` 向上；
- 单人消息包含 `source_id`、帧号、时间戳、状态和 26 个 `joints`；
- 多人消息额外包含 `stream_id` 和 `persons`，每个人包含唯一正整数 `track_id`、`observed_in_frame` 和 26 个关节。

无效关节必须使用 `null`，不能使用 `[0, 0, 0]` 代替。多人消息中 `observed_in_frame=false` 的人物会被前端整体隐藏，即使消息中错误地带有坐标也不会继续显示。

前端采用 latest-only 策略：只保留最新解析帧，不排队等待历史帧；当前 React 页面断线后约 1.5 秒重连，超过 500 ms 未收到有效帧时视为过期。联调时要区分：发布端收到的是 `system.ack`，浏览器驱动假人需要收到 `type=event`。

## 6.5 3DGS 坐标映射与出生点

humanpose 发布的是 application 坐标，平台内部的 Three.js 场景使用 Y 轴向上。转换只在前端入口执行一次：

```text
application [x, y, z] → Three.js [x, z, -y]
```

其中 application 坐标为米制、右手系、`+X` 向右、`+Y` 为前后方向、`+Z` 向上。平台的放置信息包含：

- `origin`：假人出生点，使用 3DGS 场景单位；
- `yawRadians`：绕 Three.js 场景 Y 轴的朝向；
- `realPerSceneUnit`：场景单位对应的实际米数；
- `targetHeightMeters`：假人目标身高。

实时模式下，首个可靠的脚踝中点（Halpe26 的 15、16 点）作为出生参考；脚踝不可用时回退到髋部中点（11、12 点）。首个人物放在配置的 `origin`，多人其余人物根据相对于首个人物的水平偏移计算各自出生点，并应用相同的场景缩放和 yaw。

未完成 3DGS 米制标定时，`realPerSceneUnit` 使用回退值，空间距离只能作为相对显示；要让人物与场景中的真实物体对齐，必须先完成场景比例标定。

## 6.6 假人空间移动

当前 React 实时轨道使用 `positionMode=relative`：

1. 首帧记录脚踝或髋部根节点，作为该角色的运动参考；
2. 后续帧计算根节点相对首帧的水平位移；
3. 身体关节减去根节点后用于姿态和身高缩放；
4. 根节点位移单独换算为场景单位，叠加到出生点，驱动假人在 3DGS 中行走；
5. 肢体旋转交给火柴人渲染器或 `MixamoRetargeter`，不与整体位移混在一起。

因此，humanpose 发布时必须保留连续帧中的 application 根节点位置。若在后端每帧都把人体平移到原点，前端只能看到原地动作，无法恢复空间移动。

身高缩放只作用于身体局部坐标，根节点的真实移动距离不能再次乘以身高修正系数。`origin`、`yawRadians` 和根节点位移也只能各应用一次，禁止在 humanpose、平台实体层和渲染器中重复交换坐标轴、重复旋转或重复加外参。

平台还保留 `positionMode=application` 的渲染能力，可直接保留 application 坐标中的绝对水平根位置；切换该模式时必须同步修改轨道生成逻辑，不能只修改渲染器，否则会出现出生点和根位移重复计算。

## 6.7 平台部署与运维

### 6.7.1 前端构建

前端在 x86 开发机或构建机完成编译，Nano 不负责执行 React 或 3DGS 构建：

```bash
cd /home/fr1511b/program/3DGSAlgPlatform/fronted/fronted-react
npm install
npm run build
```

构建产物为 `dist/`，部署时将其同步到 Nano 的 Nginx 静态目录。生产环境优先使用同源 `/api`，这样 WebSocket 地址会自动转换为当前页面对应的 `ws` 或 `wss`，避免跨域和混合内容问题。

### 6.7.2 网关和反向代理

Nano 上启动实时网关：

```bash
cd /home/fr1511b/program/3DGSAlgPlatform/fronted/backend-fastapi
uvicorn app.realtime_app:app --host 127.0.0.1 --port 8000 --workers 1
```

Nginx 需要同时完成两件事：

- 静态返回前端 `dist/`；
- 将 `/api/` 转发到 `127.0.0.1:8000`，其中 `/api/realtime/ws` 必须开启 WebSocket Upgrade，使用 HTTP/1.1，关闭代理缓冲并设置足够长的读写超时。

服务启动顺序为：实时网关 → humanpose 发布端 → Nginx。检查方式：

```bash
curl http://127.0.0.1:8000/api/health
```

随后打开 `/scene`，在实时面板确认 WebSocket 为 connected、topic 正确、帧率和消息年龄正常。

### 6.7.3 运维注意事项

- FastAPI 实时入口使用 `app.realtime_app:app`，不要误启动包含数据库和训练接口的 `app.main:app` 作为 Nano 实时网关；
- 修改前端后只需重新构建并替换 `dist/`；修改网关或 humanpose 后重启对应服务；
- 排查时先看 `curl /api/health`，再看 humanpose 的发布统计，最后看浏览器控制台和 WebSocket 帧；
- 若使用 systemd，分别查看实时网关、humanpose 和 Nginx 的服务日志，确认发布端和浏览器连接到了同一个 FastAPI 进程；
- 回滚时保留上一份 `dist/`、配置文件和 TensorRT Engine，先恢复前端或服务版本，再恢复模型，避免同时改变多个变量。

### 6.7.4 常见问题

| 现象 | 优先检查 |
| --- | --- |
| 页面能打开但没有姿态 | `/api/health`、humanpose 发布地址、topic 和 `event` 名称 |
| WebSocket 已连接但没有 `event` | 发布端是否发送到同一个进程，是否只看到了 `system.ack` |
| 假人出现但原地不动 | humanpose 是否每帧重置根节点，轨道是否使用 `relative`，脚踝/髋部点是否有效 |
| 假人方向或高度错误 | application→Three 转换、yaw、`realPerSceneUnit` 和 `targetHeightMeters` 是否重复应用 |
| 多人位置跳变或重复 | `stream_id`、`track_id` 是否稳定，是否在短暂丢帧时重建了实体 |
| 断线后一直重连 | Nginx Upgrade 配置、8000 端口监听、单 worker 和浏览器同源地址 |
